# LKL — поиск задач по спортивному программированию

Python **3.14**, **uv**, FastAPI без DI, SQLAlchemy, **PostgreSQL + pgvector**, React и TypeScript. Два контейнера приложения (`backend`, `frontend`) и отдельный контейнер БД. Все данные, включая теги и очередь переиндексации, находятся в PostgreSQL.

Пошаговая инструкция первого запуска и проверки приложения: [LOCAL_SETUP.md](LOCAL_SETUP.md).

## Запуск

Из корня репозитория при запущенном Docker Desktop:

```powershell
docker compose up -d --build
```

- Приложение: http://localhost:3000
- Документация API: http://localhost:8000/docs
- Проверка сервера: http://localhost:8000/api/health

По умолчанию ключи не нужны. При первом запуске пустая БД заполняется восемью небольшими демонстрационными задачами. Для пустого банка задайте `SEED_DEMO=false` **до первого запуска**. Эта настройка не удаляет уже сохранённые задачи.

Остановка с сохранением данных:

```powershell
docker compose down
```

Данные сохраняются в Docker volume `postgres_data`. Порты приложения привязаны к `127.0.0.1`; PostgreSQL наружу не опубликован. Авторизация пользователей для локальной версии не предусмотрена.

## Режимы работы и модели

Скопируйте `.env.example` в `.env` в корне репозитория. Секреты в репозиторий не добавляются.

Режимы работы:

- `LLM_PROVIDER=auto` (по умолчанию): с `LLM_API_KEY` включает Gateway, без ключа использует деморежим. `LLM_PROVIDER=demo` явно отключает вызовы LLM: сохраняются условие и переданные решения без интеллектуального анализа и проверки необходимости изображения.
- `EMBEDDING_PROVIDER=local` (по умолчанию): реальные многоязычные семантические эмбеддинги `sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`, 384 измерения, CPU через FastEmbed/ONNX. Модель скачивается один раз в Docker volume `embedding_models`; исходные тексты на сторонний сервис не отправляются. Индексируется содержимое JSON без служебных имён полей. Части документа укладываются в окно токенизатора, их нормализованные векторы усредняются. Математическая постановка получает дополнительный вес, чтобы число решений не затмевало суть задачи. Для запросов и документов используется одна модель.
- `EMBEDDING_PROVIDER=hash`: прежнее техническое ранжирование по хешированным словам и триграммам; семантической моделью не является.

Первая загрузка локальной модели требует Интернета и может занять несколько минут. Последующие запуски используют сохранённый кэш. Число CPU-потоков задаётся `EMBEDDING_THREADS` (по умолчанию 2).

Для анализа задач через предоставленный GATE:

```dotenv
LLM_PROVIDER=auto
LLM_BASE_URL=https://llm-gateway.sicamp.ru/v1
LLM_API_KEY=ваш_ключ
LLM_MODEL=nebius/Qwen/Qwen3-235B-A22B-Instruct-2507
```

Точный доступный идентификатор модели нужно взять из `GET /models` вашего Gateway. Промпты лежат в `backend/prompts/`; в них подставляется текущий закрытый список тегов. Код передаётся вместе с решениями в их исходном порядке. Ответ LLM проверяется по схеме до сохранения. Повторных платных запросов после сетевой ошибки автоматически нет.

Внешний совместимый с `/embeddings` API можно использовать вместо локальной модели:

```dotenv
EMBEDDING_PROVIDER=api
EMBEDDING_BASE_URL=https://адрес-провайдера/v1
EMBEDDING_API_KEY=ваш_ключ
EMBEDDING_MODEL=идентификатор-модели
EMBEDDING_DIMENSIONS=384
```

Проверка 18 ноября 2026 года: GATE показывает `Qwen3-Embedding-8B` в `/models`, но сам маршрут `/embeddings` возвращает `404 unsupported_route` — он отключён из-за учёта квот. Поэтому по умолчанию используется локальная семантическая модель. Для внешнего API размерность должна совпадать с ответом модели; поддерживается 8–2000 измерений. Для задач и запросов используется один и тот же провайдер и модель.

После изменения `.env`:

```powershell
docker compose up -d --build
```

Если поменялась модель с сохранением размерности, запустите «Поисковый индекс» на экране «Банк задач». До перестроения смешивание эмбеддингов разных моделей блокируется.

Если поменялась **размерность**, пересоздайте только поисковые записи и индекс транзакционно, сохранив задачи, решения и теги:

```powershell
docker compose stop frontend backend
docker compose build backend
docker compose run --rm --no-deps backend /app/.venv/bin/python -m app.manage rebuild-search
docker compose up -d
```

Команда обращается только к настроенному эмбеддеру. Убедитесь, что все переиндексации завершились до остановки сервера.

## Интерфейс

- Поиск, выбор тегов, сложности 1–10, сортировка и пагинация по 5 задач.
- Страница задачи: условие, математическая постановка, источник, решения, актуальный JSON.
- Отдельные экраны добавления и редактирования задач и решений.
- Просмотр кода и характеристик решения, отметка «Сгенерировано LLM».
- Добавление существующего или свободного тега к конкретному решению.
- Закрытый словарь с фиксированными синонимами, очередь свободных тегов.
- Переиндексация задачи, всего банка, тегов и эмбеддингов, история и состояние заданий.

Структура экранов адаптирована по присланному текстовому макету LKL. Точное визуальное соответствие Figma не проверено: доступ к файлу через браузерный инструмент получить не удалось.

## Правила данных и поиска

- Оригинальное условие хранится отдельно от JSON, исходный код — отдельно от JSON решения. `analysis.solutions` формируется из актуальных записей; он не устаревает при CRUD.
- Сложность задачи — минимум указанных сложностей решений. Задачи без решений/сложности допустимы.
- Общие теги задачи — объединение закрытых `tags` её решений. `free_tags` не входят в индекс и фильтры, пока не станут закрытыми тегами и не будут связаны с решением через `tags`.
- Теги и синонимы сравниваются без учёта регистра. Подмена синонимов в запросе учитывает границы слов и сначала длинные фразы. Словарь синонимов автоматически не расширяется.
- Несколько фильтров тегов объединяются через **OR**. Фильтр тегов и сложности — через **AND**. При отсутствии фильтра сложности допускаются задачи с неизвестной сложностью.
- В PostgreSQL сохраняются эмбеддинги JSON `statement` + `solutions` и HNSW-индекс. Выдача использует точное косинусное расстояние **после фильтрации**, чтобы не терять результаты из-за постфильтрации приближённого поиска. Обогащение запроса и реранкер — отдельные заглушки, сохраняющие запрос/порядок.
- Редактирование задачи не обращается к LLM. При добавлении через реальную LLM задача с `statement.image_required=true` отклоняется.
- При переиндексации банка существующие решения сохраняются, новые сравниваются по множеству тегов и обеим асимптотикам.
- При переиндексации одной задачи старые решения заменяются новыми; исходный код переносится по порядку входных решений. Если ответ LLM не позволяет сохранить код, операция отклоняется.
- Переиндексация тегов фиксирует очередь на старте, проверяет применимость по всем задачам, создаёт дополнительные LLM-решения и продвигает только применимые теги. Исторические `free_tags` у решений сохраняются. Из общей очереди удаляются только записи снимка; новые поступления остаются.
- Изменения каждой переиндексации применяются одной транзакцией. Ошибка LLM/эмбеддера или конкурентное изменение анализируемой задачи отменяют результат и сохраняют очередь. Состояние задания остаётся доступным в UI.

Фоновые задания выполняются в процессе API; запуск предусмотрен с **одним worker**. После перезапуска незавершённые задания помечаются ошибкой и могут быть запущены повторно. Для большого банка потребуются отдельный воркер и пакетная обработка: текущая версия накапливает результаты анализа в памяти до транзакционного сохранения.

## Импорт папки Timus через CLI

Импортёр читает папку рекурсивно: `<номер>_statement.txt` — условие, `<номер>.cpp` — исходное решение. Поддерживаются также `.cc`, `.cxx`, `.c`, `.py`, `.java`, `.pas`, `.cs`, `.kt`, `.rs`, `.go`, `.js` и несколько решений вида `<номер>_<вариант>.cpp` в той же папке. Название берётся из первой непустой строки условия, источник — ссылка на Timus. Поддерживаются UTF-8/BOM, UTF-16 с BOM и Windows-1251 (`--encoding auto` по умолчанию).

Сначала запустите приложение через `docker compose up -d --build`. Затем из корня репозитория:

```powershell
cd backend
uv run -m app.import_timus "C:\Users\pc\Downloads\drive-download-20261118T143427Z-1-001\timus-master" --dry-run
```

`--dry-run` только читает и проверяет файлы: API и LLM не вызываются, база не меняется. Пример импорта трёх конкретных задач с отчётом:

```powershell
uv run -m app.import_timus "C:\Users\pc\Downloads\drive-download-20261118T143427Z-1-001\timus-master" --ids 1007 1013 1029 --limit 3 --report .local/timus-import.json
```

Без `--ids` и `--limit` команда обработает всю папку. `--limit` ограничивает число выбранных задач, включая уже импортированные; это не число новых задач. По умолчанию используется backend `http://127.0.0.1:8000`; другой адрес задаётся `--api-url`. API-ключ LLM остаётся на backend и CLI не нужен.

Каждая задача отправляется в существующий механизм добавления вместе с найденным кодом. Реальная LLM возвращает структурированное описание, теги, сложность 1–10, асимптотику времени и памяти. Код сохраняется отдельно, строится поисковый вектор. Если кода нет, задача обрабатывается с пустым списком входных решений, и LLM может предложить решения по обычным правилам. По умолчанию импортированный код помечается `source=code`, `trusted=false`: при известном статусе AC можно указать `--trusted-solutions`. Код импортёр не запускает.

Успешная загрузка фиксируется в PostgreSQL в `import_records` с ключом `timus:<номер>` и хешем входных данных, одной транзакцией с задачей, решениями и поисковым вектором. Повторная команда возвращает `skipped`, существующий ID и не вызывает LLM повторно. Это работает и после потери ответа API или перезапуска CLI. Изменённое условие, код или флаг доверия возвращают конфликт 409: существующая задача автоматически не перезаписывается. После удаления задачи удаляется и запись импорта; её можно загрузить заново. Обычное ручное добавление задач по-прежнему допускает дубликаты.

Файлы с ошибками и отклонённые задачи попадают в отчёт, следующие задачи продолжают обрабатываться. После ошибки повторите ту же команду: успешные задачи будут пропущены. Автоматических платных повторов нет. `--report` записывает JSON после каждой задачи с номером Timus, ID в БД, результатом, ошибками и характеристиками решений. Коды завершения: `0` — успех, `1` — ошибки отдельных задач, `2` — ошибка запуска/настроек, `130` — остановка через Ctrl+C.

При наличии Docker можно запускать CLI из корня без отдельного Python на хосте:

```powershell
$timusFolder = "C:\Users\pc\Downloads\drive-download-20261118T143427Z-1-001\timus-master"
docker compose run --rm --no-deps -v "${timusFolder}:/imports:ro" backend /app/.venv/bin/python -m app.import_timus /imports --api-url http://backend:8000 --limit 3 --dry-run
```

## API

Полные схемы и примеры доступны в Swagger UI `/docs`.

| Метод | Путь | Назначение |
|---|---|---|
| GET / POST | `/api/problems` | Поиск / добавление задачи |
| POST | `/api/internal/problems` | Общий механизм добавления без UI; обязательное поле `statement`, `title` необязателен |
| GET / PUT / DELETE | `/api/problems/{id}` | Просмотр / изменение / удаление задачи |
| POST | `/api/problems/{id}/solutions` | Добавление решения |
| PUT / DELETE | `/api/problems/{id}/solutions/{sid}` | Изменение / удаление решения |
| POST | `/api/problems/{id}/solutions/{sid}/tags` | Привязка тега: `name`, `kind=closed\|free` |
| GET | `/api/tags`, `/api/tags/pending` | Закрытые / ожидающие теги |
| POST | `/api/problems/{id}/reindex` | Замена решений одной задачи |
| POST | `/api/reindex/bank` | Добавление новых решений по банку |
| POST | `/api/reindex/tags` | Обработка снимка свободных тегов |
| POST | `/api/reindex/embeddings` | Пересчёт эмбеддингов |
| GET | `/api/jobs`, `/api/jobs/{id}` | Прогресс и результат заданий |

Поиск: `q`, повторяемый параметр `tags`, `difficulty` или диапазон `difficulty_min`/`difficulty_max`, `sort=relevance\|newest\|oldest`, `offset`, `limit`.

## Разработка

Backend находится в `backend/`, frontend — в `frontend/`. Python-зависимости закреплены в `backend/uv.lock`, JavaScript-зависимости — в `frontend/package-lock.json`.

```powershell
cd backend
uv sync --locked
```

Для запуска backend вне Docker задайте `DATABASE_URL=postgresql+psycopg://user:password@host:port/database` своего PostgreSQL с расширением `vector`, затем `uv run uvicorn app.main:app --reload`. Приложение создаёт таблицы при первом старте; миграции существующих бизнес-таблиц отдельно не реализованы.

```powershell
cd frontend
npm ci
npm run dev
```

Vite проксирует `/api` на `http://127.0.0.1:8000`, поэтому можно запускать frontend в режиме разработки вместе с контейнерным backend. Продакшен-сборка: `npm run build`.

Тестовые файлы и тестовые зависимости отсутствуют по вашему требованию. Выполнены сборка frontend, сборка/запуск Compose и проверка HTTP и PostgreSQL. Визуальная проверка браузером не выполнена из-за отсутствия доступа к окну.

18 ноября 2026 года выполнены реальные запросы к GATE и ручная проверка API на отдельной временной PostgreSQL-базе с двумя короткими, специально составленными задачами. Проверены анализ с кодом и без него, CRUD решений, сохранение кода при переиндексации задачи и банка, пересчёт эмбеддингов, русские и английские поисковые запросы, фильтры, дедупликация очереди тегов, продвижение применимого тега с созданием LLM-решения и отклонение задачи без необходимого рисунка. Проверено сохранение исторических свободных тегов после продвижения и последующего редактирования решения. При единичном HTTP 502 от GATE задание завершилось ошибкой без изменения данных и очереди; повторный запуск прошёл успешно. Автоматических платных повторов нет.
